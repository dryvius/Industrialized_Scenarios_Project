# 文档驱动交付与 SSOT

## 1. 目标

把「为什么这么做、什么不做、怎么算做完」固化在同一条叙事里，使跨会话、跨人都能复现决策：

1. 每个关键事实只有一个权威文档，其他文档只能引用，不能各说一套。
2. 方案先于代码，但方案必须能落到文件与行号，不能只有口号。
3. 「明确不做」与「已做」同等重要，避免范围反复漂移。
4. 验收项可勾选、可核对，且区分「自动化可验证」与「只能人工目视」。

## 2. 执行前检查

1. 通读 `docs/` 下现有文档的标题结构，确认主题边界。
2. 找出**互相冲突**的表述。典型例子：动画文档早期写「不做物理」，物理文档后来接管了空间约束。
3. 确认每个主题当前的 SSOT 归属：

| 主题 | SSOT 文档 |
|---|---|
| 视觉与场景基线 | `docs/工业基建施工场景-项目生成说明.md` |
| 动作系统 | `docs/场景动画与动作实现说明.md` |
| 空间约束与物理 | `docs/场景穿模与物理碰撞方案说明.md` |
| 人员网格与比例 | `docs/人员模型优化方案说明.md` |
| 杆塔攀爬与挂点 | `docs/杆塔高空作业实现说明.md` |
| 挖掘机部件与朝向 | `docs/挖掘机模型优化方案说明.md` |
| 全息与健康模块 | `docs/全息人体生命体征可视化模块.md` |
| 病毒三维监控面板 | `docs/病毒健康监控全息面板方案说明.md` |

4. 逐条核对代码现状，记录文件与行号。文档里的每个结论都要能指回代码。
5. 明确哪些验收能自动跑（类型检查、构建），哪些只能人工看（构图、穿模、帧率）。
6. 确认是否存在未完成项（如阶段 4 骨骼动画、Escape 关闭、臂节碰撞体），它们必须继续留在「不做 / 未做」里。

## 3. 开发流程

### 步骤一：写结论摘要表

开头用一张表回答「这些问题现在是什么结论」，让人不读全文也能决策。

| 问题 | 结论 |
|---|---|
| 穿模是不是渲染 bug | 不是，是缺少空间约束层 |
| 要不要上物理引擎 | 上，Rapier，移动体先用 Kinematic |

### 步骤二：写现状盘点

按「能力矩阵」组织，每行给：能力、是否存在、说明、关键代码位置。

- 必须带文件路径，必要时带行号或函数名。
- 不能只写「已实现」，要写清楚实现到什么程度（示意级 / 完整 / 待补）。

### 步骤三：做方案对照，再定主方案

至少列三个方案，按「真实度 / 工程量 / 性能风险 / 维护成本」对比，然后明确选一个，并写出**为什么不是另一个**。

```text
L0 手写避让 + 统一布局    低成本，立刻见效，但加实体易再穿
L1 XZ 软检测              能拦，但不像真实物理
L2 幅度夹紧              专治机构与脚穿地，与物理正交
P  真实物理（Rapier）      运行时真相来源，成本最高
```

选型后必须补一句边界：轻量方案不是废弃，而是「过渡与降级兜底」。

### 步骤四：拆阶段，每阶段可独立验收

每个阶段写清四件事：

1. 目标（一句话）。
2. 改动清单（文件级）。
3. 验收标准（可观察的现象）。
4. checkbox（完成后勾选，并记录日期）。

阶段之间要有依赖顺序：先止血与数据 SSOT，再引擎，再移动体，最后机构精修。

### 步骤五：写「明确不做」

这一节不是免责，而是防止范围漂移。每条要写清「不做的原因」，例如：

- 不做电影级物理（与示意级视觉定位冲突）。
- 不做逐网格碰撞（性能不可接受）。
- 不把物理 API 暴露给 Vue 与 Pinia（会破坏分层）。

### 步骤六：写验收 Checklist

分三组：

- **视觉 / 观感**：只能人工看，必须写清看什么（构图、穿模、光圈、色彩）。
- **工程**：能自动或半自动（构建通过、模块落位、单一数据源）。
- **运行**：命令级（`npm install / dev / build / preview`）。

凡是无法自动化的项，**不要假装有测试覆盖**。

### 步骤七：声明 SSOT 与冲突处理

- 在文首或专章写明「本文档是 XX 的 SSOT」。
- 如果与旧文档冲突，必须点名旧文档的哪句话被覆盖，以及保留旧文档的原因（历史记录 / 其他主题仍有效）。
- 更新交叉引用，避免读者顺着链接读到相反结论。

### 步骤八：登记进度

文末维护进度表：

| 日期 | 范围 | 说明 |
|---|---|---|
| 2026-10-14 | P0 | 布局 SSOT + 避让路径 |
| 2026-10-14 | P1 | 物理世界与静态体 |

每次改动补一行，不覆盖历史。文档末尾留一行「当前版本状态」，说明哪些阶段已落地、哪些是可选项。

### 步骤九：提交前自检

1. 每个结论是否能指回代码或明确标注为推测。
2. 是否有两个章节对同一事实给出不同说法。
3. 是否有「已勾选但实际未实现」的项。
4. 是否有未标注的「待确认」。
5. 术语是否与代码一致（`SITE_LAYOUT`、`RootPoseDriver`、`runState` 等）。
6. 新增文档是否已加入 README 的文档索引。

## 4. 约束

- 不得把未经验证的推测写成项目规范；不确定的一律标「待确认」。
- 不得只写设计不写落地证据（文件、函数、行号）。
- 不得让两篇文档对同一事实各下结论；必须显式声明谁覆盖谁。
- 不得把 checkbox 的勾选当成「已通过自动化验证」。
- 不得把某一模块的业务参数写成全局规范（例如生命体征阈值只适用于演示分级）。
- 不得删除历史进度记录来「让文档看起来干净」。
- 不得在文档中承诺未排期的实现。

## 5. 最终交付

完成任务后，说明：

1. 新增或修改了哪些文档，以及各自的主题边界。
2. 本文档声明的 SSOT 范围，以及与哪些既有文档存在覆盖关系。
3. 结论摘要与主方案选型理由（含被放弃的方案）。
4. 阶段划分与当前完成状态，未完成项是否仍留在「不做 / 未做」。
5. 验收 Checklist 中哪些可自动验证、哪些只能人工目视。
6. 待确认清单。
7. 是否更新了 README 的文档索引与交叉引用。
